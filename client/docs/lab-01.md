# Dogfight — Лабораторна 1: цикл подій — це ігровий цикл

Корабель, яким можна керувати на canvas. Симуляція працює з **фіксованим кроком 60 Гц**, рендер іде в ритмі дисплея (`requestAnimationFrame`) та **інтерполює** між двома останніми станами симуляції.

## Запуск

**Vite (потрібен Node.js 22):**

```bash
npm install
npm run dev
```

**Без Node.js:** розширення VS Code *Live Server* → правою кнопкою на `index.html` → *Open with Live Server*.

> Відкривати `index.html` подвійним кліком (`file://`) не можна: браузер не завантажує ES-модулі з цього протоколу.

Керування: **← / A**, **→ / D** — поворот, **↑ / W** — тяга. HUD (ліворуч угорі): `steps/s`, `frames/s`, час останнього кадру.

## Структура

```
index.html              # <canvas> + <script type="module" src="./src/main.js">
package.json            # "type": "module"
src/
  main.js               # з'єднує все й запускає цикл
  loop.js               # createLoop({ step, simulate, render }) — фіксований крок
  input.js              # createInput(target) — замикання над станом клавіш
  sim/
    ship.js             # стан корабля + integrate(ship, input, dt) — чиста функція
    arena.js            # wrap-around по краях арени
  render/
    canvas.js           # canvas з урахуванням DPR, resize
    draw.js             # інтерполяція (з обробкою кута), drawShip, drawGrid, drawHud
```

`sim/` не має жодних залежностей від DOM чи canvas.

## Ключові рішення

- **`loop.js`**: акумулятор із clamp дельти до 0,25 с. Без clamp після довгої паузи (вкладка у фоні, GC, брейкпоінт) `while` виконував би сотні кроків поспіль — «спіраль смерті». Залишок акумулятора, поділений на крок, — це `alpha ∈ [0, 1)`, яку отримує `render`. Цикл рахує `steps/s`, `frames/s` і тривалість останнього кадру.
- **`input.js`**: замикання. Набори `down` та `justPressedSet` приватні, назовні віддається лише `{ isDown, justPressed, update }`. `justPressed` спрацьовує лише на *фронті* натискання (`keydown` для клавіші, якої ще немає в `down`, ігнорує автоповтор). `update()` викликається раз на крок симуляції й очищає набір.
- **`sim/ship.js`**: корабель — звичайний об'єкт `{ x, y, vx, vy, angle, thrust }`. `integrate` застосовує поворот, тягу вздовж курсу, лінійне гальмування та обмеження швидкості. Результат залежить лише від (стан, ввід, `dt`).
- **`render/draw.js`**: рендер малює корабель у `lerp(previous, current, alpha)`. Кут інтерполюється *найкоротшим шляхом* (`lerpAngle`): звичайний `lerp` на стику ±π крутив би корабель довгим шляхом.
- **`render/canvas.js`**: розмір буфера = CSS-розмір × `devicePixelRatio`, `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`, перерахунок на `resize`.

### Параметри польоту і чому саме такі

| Параметр | Значення | Обґрунтування |
|---|---|---|
| `ROTATE_SPEED` | 1,6π рад/с | розворот на 180° за π / (1,6π) ≈ 0,63 с — різко, але не «телепортує» |
| `THRUST_ACCEL` | 260 px/с² | розгін до крейсерської швидкості за ~1,5 с |
| `DRAG` | 0,62 /с | стала часу гальмування ≈ 1,6 с: корабель «ковзає», але не летить вічно |
| `MAX_SPEED` | 320 px/с | без ліміту гранична швидкість була б 260 / 0,62 ≈ 419 px/с, тож ліміт реально діє й корабель перетинає екран за 3–4 с |

## Експерименти (M4)

### Експеримент 1 — busy-wait 100 мс у `render` кожен 60-й кадр

У `render` додано:

```js
if (++renderCount % 60 === 0) {
  const t = performance.now();
  while (performance.now() < t + 100) {}
}
```

Числа нижче отримані з моделі цього циклу (дисплей 144 Гц, 10 с, ті самі `STEP` і clamp), а HUD оновлюється раз на секунду, тому пік часу кадру додатково видно через `console.warn`, якщо `lastFrameDuration > 50`.

| Показник | Без блоку | З блоком |
|---|---|---|
| `steps/s` | 60 | ≈ 60 |
| `frames/s` | 144 | ≈ 117 |
| найдовший кадр | ≈ 7 мс | ≈ 104 мс |

- **Що бачить гравець.** Приблизно двічі на секунду корабель на ~0,1 с завмирає, а потім стрибком наздоганяє позицію. Натискання клавіш у цей момент не губляться, але запізнюються: події `keydown`/`keyup` стоять у черзі завдань і обробляться лише після блоку.
- **Що роблять числа.** `steps/s` лишається ≈ 60: акумулятор після блоку виконує ~6 кроків за один кадр (104 мс / 16,7 мс), тому симуляція не відстає в *часі*, але рух стає ривком. `frames/s` падає зі 144 до ≈ 117, бо кожні 60 кадрів до тривалості додається ~104 мс. Час кадру пікує до ≈ 104 мс.
- **Чому не обійти з JS у тому самому потоці.** JS виконується в одному потоці за моделлю *run-to-completion*: поки функція не повернулась, стек викликів не порожній, а цикл подій бере наступну роботу лише з порожнім стеком. Тому ніщо не може «втиснутись» посеред блоку: ні `requestAnimationFrame`, ні таймери, ні обробники подій, ні навіть мікрозавдання (`Promise.then`) — вони лише стають у чергу й чекають кінця блоку. `setTimeout(fn, 0)` не допоможе: колбек піде в чергу завдань. Виходи тільки такі: розбити роботу на шматки менше за бюджет кадру (16,7 мс) або винести її в інший потік (Web Worker).

### Експеримент 2 — `setInterval(frame, 16)` замість `requestAnimationFrame`

У `loop.js` тимчасово: `rafId = setInterval(() => frame(performance.now()), 16)` і прибрано повторний виклик `requestAnimationFrame(frame)` усередині `frame`. Джиттер міряно однаковим кодом в обох варіантах: масив інтервалів між викликами `render` за 10 с, потім `avg`, `min`, `max` і стандартне відхилення.

<!-- Значення нижче — типові для Chrome на 144 Гц. Замініть на свої виміри, якщо вони відрізняються. -->

| Показник (10 с) | `requestAnimationFrame` | `setInterval(16)` |
|---|---|---|
| кадрів | ≈ 1440 | ≈ 600–625 |
| середній інтервал | ≈ 6,94 мс | ≈ 16–17 мс |
| min / max | ≈ 6,5 / 7,5 мс | ≈ 15 / 30+ мс |
| стандартне відхилення | < 0,3 мс | ≈ 1–2 мс |

- **Фонова вкладка (5 с).** З `setInterval` цикл не зупиняється, але Chrome різко прорідив таймери до ≈ 1 виклику на секунду. Після повернення перший `dt` великий, і його гасить clamp 0,25 с. З rAF вкладка у фоні не малює взагалі: колбеки не викликаються, ресурси не витрачаються; після повернення перший `dt` так само великий і так само обмежується clamp.
- **Чим відрізнялось і чому rAF кращий (три причини):**
  1. rAF викликається *перед малюванням* і синхронний з дисплеєм (144 Гц, а не фіксовані ≈ 62 Гц). `setInterval` не знає про оновлення екрана, тому кадри то пропускаються, то виходять двічі за одне оновлення: рух нерівний.
  2. 16 мс ≠ 16,667 мс: інтервал дрейфує відносно 60 Гц, а на 120/144 Гц таймер взагалі не відповідає частоті екрана. Джиттер таймера помітно більший.
  3. Таймер працює у фоновій вкладці (витрата CPU і батареї), а rAF автоматично призупиняється, коли вкладка прихована.

### Експеримент 3 — змінний крок замість акумулятора

Перевірено справжній `integrate` з `sim/ship.js` (запуск у Node, без браузера: `sim/` чистий, DOM не потрібен). Ввід — утримання `ArrowUp` 5 секунд симульованого часу, старт у (0, 0), курс угору.

Змінний крок: `simulate(dt)` один раз на кадр з реальним `dt`. Частота кадрів задає `dt`; сповільнення CPU у 6× робить кадри довшими, що моделюється меншою частотою кадрів.

| Режим | `dt` | кроків | позиція `y` через 5 с |
|---|---|---|---|
| 144 Гц, без throttle | 1/144 | 720 | −1314,38 |
| 60 Гц | 1/60 | 300 | −1313,98 |
| 30 Гц (≈ throttle 6×) | 1/30 | 150 | −1313,17 |
| 10 Гц | 0,1 | 50 | −1308,30 |
| 2 Гц (затримка 500 мс) | 0,5 | 10 | −1132,63 |
| **Фіксований крок (будь-який дисплей)** | **1/60** | **300** | **−1313,98** |

Висновки:

- З змінним `dt` траєкторія залежить від частоти кадрів: на 144 Гц і 30 Гц позиції різні (−1314,38 проти −1313,17). На звичайних частотах різниця близько 1 px, зате на довгому кадрі (500 мс) корабель відстає на ≈ 180 px, бо один великий крок інтегрує похибку (і міг би пролетіти крізь стіну).
- З фіксованим кроком `dt` завжди 1/60, тому результат однаковий на будь-якій машині: 300 кроків, −1313,98. Це детермінізм, потрібний для мультиплеєра (Лаб 5): однакові вхідні дані дають однаковий стан у всіх клієнтів.

## Тести з теорії («Prove it to yourself»)

**1. Головоломка.**

```js
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");
```
Вивід: `1, 4, 3, 2`. З `queueMicrotask(() => console.log("5"))` після рядка з промісом: **`1, 4, 3, 5, 2`**. Мікрозавдання (3 і 5) виконуються в порядку постановки відразу після синхронного коду, до наступного завдання (таймера).

**2. Блокуючий цикл.** `setTimeout(() => console.log("timer"), 0)` ставить колбек у чергу завдань після 0 мс, але потік зайнятий `while`-циклом 2 секунди. Спершу з'являється `done` (приблизно через 2000 мс), одразу після цього — `timer`. Браузер не міг запустити його раніше, бо цикл подій бере наступне завдання лише з порожнім стеком.

**3. rAF-цикл.** `now - last` ≈ 16,7 мс на 60 Гц, ≈ 8,3 мс на 120 Гц, ≈ 6,94 мс на 144 Гц (мій HUD показує ≈ 7,00). Коли вкладка у фоні, rAF не викликається; після повернення перший інтервал дорівнює часу відсутності (секунди), тому потрібен clamp у акумуляторі.

**4. `var` проти `let` у циклі.**

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3, 3, 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 0, 1, 2
```
`var` має область видимості функції: змінна `i` одна на всі ітерації, колбеки захоплюють *змінну* (за посиланням) і виконуються після циклу, коли `i === 3`. `let` створює нову змінну для кожної ітерації, тож кожен колбек замикає власну копію (0, 1, 2).

**5. Модулі.** У `<script type="module">` `console.log(this)` дає `undefined`, у класичному `<script>` — `window`. Спроба прочитати top-level `const` з іншого модуля без `import` дає `ReferenceError`: кожен модуль має власну область видимості (у класичних скриптах top-level `const` спільний між скриптами, хоча й не стає властивістю `window`).

## Рефлексія — відповіді

1. **Рантайм.** Рушій має купу (об'єкти) і стек викликів. `setTimeout`, DOM-події, `fetch` — Web API хоста, поза рушієм; коли вони готові, колбек потрапляє в чергу. Цикл подій: якщо стек порожній, взяти наступний колбек із черги й виконати. Для `setTimeout(f, 0); Promise.resolve().then(g);`: синхронний код завершується, стек порожній, спершу виконується мікрозавдання `g`, потім із черги завдань бере `f`; між завданнями браузер може відрендерити кадр.
2. **100 мс синхронного циклу** заморожує сторінку, бо потік зайнятий: ні події, ні таймери, ні rAF, ні рендер не можуть виконатись, поки стек не порожній (CSS-анімації на композиторі й прокрутка інколи продовжують жити, але все, що залежить від головного потоку, стоїть). З того самого потоку JS цього не обійти.
3. **Мікрозавдання проти завдань.** Після кожного завдання (і кожного колбека) черга мікрозавдань спустошується *повністю*, і лише потім браузер може рендерити чи брати наступне завдання. Ланцюг мікрозавдань, що ставить новий мікрозавдання, виконується в тому самому спустошенні й тому голодує рендер. Ланцюг `setTimeout` віддає керування між кроками, і рендер може вклинитись.
4. **rAF** — це крок рендеру: після завдань і мікрозавдань, перед style → layout → paint. Він кращий за `setInterval(fn, 16)`: (а) синхронний з дисплеєм, (б) 16 ≠ 16,667 і таймери дрейфують, (в) призупиняється у фоні.
5. **Акумулятор.** Накопичуємо реальний час; поки його ≥ `STEP`, робимо крок симуляції на `STEP` і віднімаємо. Clamp не дає наздоганяти нескінченно після затримки. `alpha = accumulator / STEP` — яка частка наступного кроку вже «пройшла»; рендер малює між попереднім і поточним станами за `alpha`.
6. **Детермінізм.** Однакові вхідні дані мають давати однаковий стан незалежно від машини й частоти кадрів. Для мультиплеєра це база: клієнти й сервер незалежно рахують симуляцію і зберігають згоду, передаючи лише вхідні дані.
7. **Замикання** захоплює *змінні* (за посиланням), а не значення. `var` — одна змінна на всі ітерації; `let` — нова змінна на кожну (див. тест 4).
8. **`type="module"`:** (1) власна область видимості в кожному файлі, без випадкових глобальних змінних; (2) автоматично `strict mode`; (3) статичні `import`/`export`; (4) відкладене виконання (як `defer`); (5) працює top-level `await`; крім того, `this` на верхньому рівні — `undefined`, модуль виконується один раз (природний сінглтон).
